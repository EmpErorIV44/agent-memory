# Схема SQLite

`001_initial.sql` создаёт начальную схему v0.1, `002_memory_projection.sql`
добавляет пересоздаваемую проекцию Memory/Evidence/Relation и последовательности
внутренних ID. Требуется SQLite 3.38 или новее с FTS5 (`STRICT`, `unixepoch()` и
`RETURNING`). Текущая версия `PRAGMA user_version` — 2.

При старте приложение читает версию, для обновления получает `BEGIN IMMEDIATE`
и повторно проверяет версию под блокировкой: одновременные клиенты не запускают
одну миграцию дважды. Начальная схема и необходимые обновления применяются одной
транзакцией; ошибка откатывает изменения. Существующие документы и FTS сохраняются.
SQL-файлы также можно применять отдельно в порядке версий: они содержат собственные
транзакционные обёртки, которые приложение исключает при выполнении внутри своей
транзакции. Повторное прямое применение миграции намеренно завершается ошибкой.

## Настройка соединений

До миграции и до начала любых транзакций:

```sql
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
PRAGMA journal_mode = WAL;
```

`foreign_keys` и `busy_timeout` нужно устанавливать для каждого соединения.
WAL сохраняется у файла базы; при открытии приложение проверяет полученный режим
(`:memory:` не поддерживает WAL). WAL допускает читателей во время записи,
но не координирует задания индексатора. Проверку хеша, обновление документа и
замену всех его фрагментов выполнять одной транзакцией с координацией писателей.
Параметры PRAGMA намеренно не спрятаны внутри миграции.

## Модель

- `projects` задаёт именованные пространства доступа.
- `sources` хранит канонический абсолютный путь зарегистрированной директории.
- `project_sources` связывает источник с любым числом проектов и разделяет
  разрешения чтения и записи. По умолчанию источник доступен только для чтения.
- `documents` описывает физический файл внутри источника. `content_hash` — SHA-256
  исходных байтов файла в нижнем регистре; `file_mtime_ns` — время изменения в
  наносекундах Unix; `byte_size` — размер. Хеш определяет изменение содержимого,
  время и размер служат подсказками, а не доказательством неизменности.
- `stable_id` — необязательный `id` из frontmatter, уникальный внутри источника.
  Копии в разных источниках допустимы. Дубликат внутри источника — диагностируемая
  ошибка индексирования. ID извлекается из YAML при чтении источника; переименование
  с сохранённым ID сохраняет идентичность документа. Замена явно заданного ID —
  удаление старой идентичности и добавление новой. Документы без ID поддерживаются
  по пути. При миграции метаданные дополняются даже при неизменённом хеше.
- `document_chunks` хранит поисковые фрагменты, заголовок и включительные номера
  строк исходного Markdown, начиная с 1. `ordinal` начинается с 0.
- `document_chunks_fts` — external-content FTS5; триггеры синхронизируют вставки,
  изменения и удаления, включая каскадное удаление документов/источников.
  `unicode61` поддерживает Unicode, но не выполняет русскую морфологию.

`created_at` и `indexed_at` — секунды Unix UTC. Для восстановления индекса нужны
Markdown и сохранённая отдельно конфигурация регистрации проектов, источников и
прав: миграция не восстанавливает её из самих файлов. При `rebuild` конфигурация владельца атомарно восстанавливает регистрации,
права, документы, FTS и структурированные знания; сведения из Markdown не создают
проекты и не предоставляют разрешения. Исторические ревизии и долговечный журнал
авторских изменений — отдельные будущие возможности.

## Структурированные знания

В YAML допускается отдельный блок `memory` с собственным `id`, явным `project`,
`kind`, `status`, `summary`, `evidence` и `relations`. ID логической Memory отличается
от ID документа; один документ может описывать одну Memory. Исходные данные остаются
в Markdown, а таблицы `memories`, `memory_evidence`, `memory_relations` — проекции,
восстанавливаемые индексацией. Сочетание `(project_id, memory_id)` уникально.

Обычный `index --project` обновляет структурированные записи только выбранного
проекта. Так устаревшая запись чужого приватного источника не блокирует индексацию
общего источника. При изменении физического документа его старые структурированные
записи инвалидируются для всех привязок; переименование без изменения байтов
сохраняет их. Владелец через `rebuild` обновляет все явно разрешённые проекты.

`id_sequences` выделяет возрастающие INTEGER ID для проектов, источников,
документов и chunks. Удаление или отзыв доступа не позволяют повторно использовать
ID в течение жизни SQLite; сохранённые ссылки на chunks не начинают указывать на
новый документ с такими же байтами. Неизменённые регистрации и документы при
`rebuild` сохраняют ID. После полного удаления базы постоянными идентификаторами
остаются только авторские ID из Markdown.

## Граница доступа

Приложение сначала получает авторизованный набор проектов. Переданный клиентом
`project_id` или `scope=global` сам по себе не является разрешением. Для одного
уже авторизованного проекта поиск выглядит так (все значения связаны параметрами):

```sql
SELECT c.id, d.id AS document_id, d.relative_path,
       c.heading, c.body, c.start_line, c.end_line
FROM document_chunks_fts
JOIN document_chunks AS c ON c.id = document_chunks_fts.rowid
JOIN documents AS d ON d.id = c.document_id
WHERE document_chunks_fts MATCH :query
  AND EXISTS (
      SELECT 1 FROM project_sources AS ps
      WHERE ps.source_id = d.source_id
        AND ps.project_id = :authorized_project_id
        AND ps.can_read = 1
  )
ORDER BY c.id
LIMIT :limit;
```

Для глобального поиска использовать такой же `EXISTS` с разрешённым набором ID;
при пустом наборе сразу возвращать пустой результат. `EXISTS` не дублирует
документы источника, доступного через несколько проектов. Прямой `memory_get`
по ID документа или фрагмента обязан содержать ту же проверку источника **в SQL**,
до чтения текста или файла с диска. SQLite не предоставляет здесь row-level security:
изоляцию обеспечивают прикладные сервисы и корректные запросы.

Структурированные `list/get` проверяют и проект Memory, и `can_read` её документа
до чтения полей. Связи выдаются только к существующим читаемым Memory в том же
проекте. Ссылки Evidence типа `document` выдаются только если путь или стабильный
ID разрешается в читаемый документ проекта. Остальные Evidence — непроверенные
ссылки автора: приложение не открывает URL/файлы и не запускает тесты автоматически.
Запись через проект A не может объявить `memory.project: B`, даже для общего
физического источника.

Удаление проекта удаляет его привязки, но сохраняет физические источники и
документы, которые могут быть доступны другим проектам. Удаление источника
каскадно очищает документы, фрагменты и FTS. Удаление Markdown-файла индексатор
отражает удалением соответствующего `documents` в транзакции.

## Пути и запись

До регистрации приложение канонизирует путь, учитывая регистр и особенности
Windows. `relative_path` хранится с `/`; запрещены абсолютные пути, `..`, пустые
компоненты и выход за корень. Проверка реального разрешённого пути, symlink/junction
и защита от подмены пути при открытии файла — обязанности файлового адаптера;
SQL-проверка непустого пути их не заменяет. Источники с перекрывающимися корнями
требуют явной политики регистрации, иначе один физический файл может получить
несколько представлений.

Любая запись в Markdown должна отдельно проверить авторизованный проект,
`can_write` и глобальную настройку разрешения записи агентам. Регистрация
источников и изменение прав — управляющие операции, недоступные через поиск.
Содержимое Markdown является недоверенными данными.

## Проверка начальной миграции

Проверено на SQLite 3.53.1 в памяти: применение и отклонение повторного применения,
FTS-вставка/обновление/удаление, каскадная очистка FTS, изоляция двух проектов и
отказ чтения при `can_read=0`, ограничения FK/CHECK, откат документа вместе с FTS,
`foreign_key_check`, `integrity_check` и FTS5 `integrity-check` с проверкой
external content. Это историческая проверка начальной схемы. Текущие CLI, файловый адаптер, MCP,
миграции, восстановление и структурированные проекции проверяются тестами Cargo.
