# Синхронизация Markdown через Git

Git sync сохраняет изменения Markdown отдельного источника в коммит и выполняет
обычный `git push` в настроенный upstream. Это отдельная возможность от проверки
Git Evidence: она не проверяет свидетельства об исходном коде и не определяет
истинность заметок. Это также не daemon и не двусторонняя синхронизация:
автоматических `pull`, merge и force push нет.

## Явное включение владельцем

Для MCP синхронизация выключена по умолчанию. Владелец включает её для конкретных
источников аргументами запуска, а не содержимым Markdown. Нужны `--allow-write`
и право записи в источник для разрешённого проекта. Узнайте реальный ID через
`source list --project PROJECT` или `memory_sources` и подставьте его вместо `1`:

```sh
agent-memory --database /absolute/path/memory.sqlite mcp \
  --project agent-memory --allow-write --write-policy confirm \
  --git-sync-source 1 --git-sync-interval-secs 900
```

`--git-sync-source ID` можно повторить для нескольких источников. Интервал задаёт
`--git-sync-interval-secs N` либо переменная окружения
`AGENT_MEMORY_GIT_SYNC_INTERVAL_SECS`; аргумент имеет приоритет. По умолчанию —
900 секунд. Таймер работает только пока жив MCP-процесс. Закрытие клиента или
остановка его MCP-подключения прекращает периодические попытки синхронизации.

Чтобы дополнительно синхронизировать выбранный источник после успешного
`memory_write` или `memory_restore`, добавьте `--git-sync-after-write`.
Сохранённый Markdown синхронизируется и при предупреждении об обновлении индекса.
Эти параметры не меняют политику `confirm`/`verified` и не разрешают агенту
сохранять посторонние знания без действующего разрешения.

## Однократный запуск

CLI выполняет одну попытку для явно выбранного проекта и источника:

```sh
agent-memory --database /absolute/path/memory.sqlite git-sync \
  --project agent-memory --source-id 1
```

Перед первым запуском владелец самостоятельно настраивает Git-репозиторий,
identity для коммитов, remote, upstream текущей ветки и доступ к remote.
Команда может публиковать данные: используйте её только для источника,
синхронизацию которого вы намерены выполнить.

## Какие файлы затрагиваются

Корень источника должен совпадать с корнем Git-репозитория. Репозиторий в
родительском каталоге не используется. Учитываются изменения видимых `.md`
файлов: tracked, untracked и удалённые, с соблюдением правил ignore.
Скрытые пути, `.agent-memory-history/`, SQLite и прочие файлы не добавляются.

Уже подготовленные в Git index изменения приводят к отказу: синхронизация
не смешивает их со своим коммитом. Также отклоняются конфликтное состояние,
detached HEAD и отсутствие upstream. При изменениях remote, требующих pull,
обычный push завершится ошибкой; разрешение расхождений остаётся владельцу.

## Результат и ошибки

Однократный CLI при успехе выводит `{"status":"ok","source_id":1}` (с реальным ID). Ошибки периодического
запуска выводятся в stderr, оставляя stdout для MCP. При включённой синхронизации
после записи в выбранный источник ответ содержит `git_sync`:

```json
{"git_sync":{"status":"ok"}}
```

При ошибке Git поле имеет вид
`{"git_sync":{"status":"error","error":"описание ошибки"}}`.
При выключенном режиме или для невыбранного источника поля `git_sync` нет.
Ошибка Git не отменяет уже сохранённый Markdown: не повторяйте `memory_write`
или `memory_restore` только ради повторного push. Исправьте причину и выполните
однократный `git-sync` либо дождитесь следующего интервала.

Отдельно проверяйте `indexed` и `index_error`: публикация в Git и обновление
SQLite — разные операции. Git sync не заменяет резервную копию долговечной
истории ревизий, поскольку `.agent-memory-history/` не включается в коммиты.
