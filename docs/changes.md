# Изменения памяти во время сессии

Журнал наблюдает локальные файлы. Для знаний, получаемых через Git с другой
машины, сначала нужна [проверка remote и при необходимости pull](git-pull.md).
MCP явно возвращает `remote_checked=false`, `scope=local_markdown`.

`memory_changes` обнаруживает изменения Markdown при опросе. В начале работы
вызовите `memory_changes({"project":"agent-memory"})`: ответ содержит пустой
`changes`, текущую числовую `revision` и непрозрачный `cursor`.
После чтения релевантных знаний повторяйте вызов на границах задач и перед
решениями, зависящими от памяти, передавая `since` с последним курсором.
После обработки страницы сохраняйте новый курсор. Пока `has_more=true`,
продолжайте опрос с ним: ответ ограничен 100 событиями, включая случай,
когда одна ревизия занимает несколько страниц.

```json
{"project":"agent-memory","since":"<cursor из предыдущего ответа>"}
```

Каждая успешная индексация с изменениями увеличивает ревизию затронутого
проекта один раз. Неизменившиеся файлы, повторное чтение и изменение только
mtime ревизию не увеличивают. Журнал общий для MCP-клиентов одной SQLite.
Внешние правки обнаруживаются при следующем сканировании; промежуточные правки
между сканированиями не сохраняются. Это журнал наблюдений, а не watcher.

События: `added`, `updated`, `renamed`, `deleted`. Они содержат `source_id`,
`document_id`, путь, хеш и необязательный стабильный ID документа.
Переименование распознаётся по frontmatter `id`; без него получается удаление
и добавление. Если при переименовании изменился текст, событие `renamed`
содержит новый хеш и `previous_path`. Для удаления хеш относится к последнему
наблюдавшемуся содержимому. Ответ не содержит текста заметок: прочитайте
релевантные знания через поиск и чтение. Возможны несколько событий одной
заметки, включая её последующее удаление. Если состояние ещё актуально,
`chunk_id` позволяет вызвать `memory_get` с хешем из события. Для устаревших
состояний и удалений `chunk_id=null`; это не историческое чтение.

Курсор привязан к проекту и экземпляру индекса, сохраняется после перезапуска
MCP. Неверный, чужой или будущий курсор отклоняется. После пересоздания SQLite
нужно получить новую базовую точку и перечитать релевантную память. Rebuild
существующей базы сохраняет курсоры и регистрирует наблюдавшиеся изменения.
Миграция v4 → v5 создаёт журнал; прежние правки задним числом не восстанавливаются.
Ошибка сканирования откатывает индекс и журнал вместе.

События фильтруются по текущим правам чтения источников. Отзыв доступа не
является уведомлением об удалении: клиент должен очищать локальный кеш при
изменении конфигурации доступа. Абсолютные пути источников не возвращаются.
Журнал пока не очищается; для длительных сессий рекомендуется регулярный опрос.

CLI:

```sh
agent-memory memory changes --project agent-memory
agent-memory memory changes --project agent-memory --since '<cursor>'
```
