# Проверка alpha

Это порядок приёмки локальной установки, а не отчёт об уже выполненных
проверках. Выполняйте запись, восстановление и Git sync на отдельном тестовом
источнике. Создание release или Git tag в этот порядок не входит.

## Установка и диагностика

Соберите бинарник, зарегистрируйте проект и источник, экспортируйте конфигурацию
владельца. Настройте MCP-клиент с абсолютными путями и перезапустите подключение;
для Windows см. [пример конфигурации](../examples/mcp-windows.json).

```sh
agent-memory --database /absolute/path/memory.sqlite doctor --project agent-memory
```

`doctor` открывает существующую SQLite только для чтения и возвращает JSON с
`healthy` и `checks`. Ошибка проверки означает ненулевой код завершения.
Диагностика Git необязательна и локальна: команда не делает fetch и не обращается
к сети. Успешный `doctor` не доказывает доступность remote или работоспособность
ещё не проверенного MCP-клиента.

## Приёмка MCP

1. Подключитесь, прочитайте `memory_list` и соответствующие полные документы.
   Найдите известную заметку через `memory_search` и проверьте полный `memory_get`.
2. Через `memory_write` создайте тестовую заметку и обновите её с актуальным
   `document.content_hash` в `expected_hash`. Повторная запись с устаревшим
   хешем должна отклоняться, сохраняя текущий текст.
3. Добавьте обоснованную ссылку на другую тестовую заметку. Проверьте исходящую
   и вычисленную обратную ссылку через `memory_links`.
4. Прочитайте историю через `memory_history` и снимок через `memory_revision_get`.
   Восстановите выбранный снимок через `memory_restore` с текущим хешем:
   результат должен стать новой ревизией, сохранив более позднюю историю.

Если запись сообщает `indexed=false` или предупреждение о сохранённой истории,
проверяйте уже опубликованный файл перед повторным действием. Ошибка последующей
операции не означает, что Markdown не был сохранён.

## Git sync и его статус

Проверьте Git sync в отдельном локальном репозитории с локальным bare upstream,
а не на рабочих remote. Порядок включения и ограничения описаны в
[Git sync](git-sync.md). Проверьте успешный push и отказ при заранее
подготовленных изменениях в Git index.

Сохранённый результат последней попытки доступен отдельно:

```sh
agent-memory --database /absolute/path/memory.sqlite git-sync-status \
  --project agent-memory --source-id 1
```

В MCP используйте `memory_sync_status({"project":"agent-memory","source_id":1})`.
Ответ имеет вид `{"source_id":1,"sync":null}`, если попыток ещё не было
или источник не является Git-репозиторием. В остальных случаях `sync` содержит:

```json
{
  "status": "ok",
  "last_attempt_at": 1793300000000,
  "last_success_at": 1793300000000,
  "last_error": null
}
```

`status` принимает `running`, `ok` или `error`. Время — Unix milliseconds;
`last_success_at` равно `null`, пока успешных попыток не было. `last_error`
содержит безопасное описание последней ошибки либо `null`. Повреждённый файл
статуса возвращает ошибку чтения, а не состояние «попыток не было».

Чтение статуса не запускает синхронизацию, fetch или сетевую диагностику.
Результат сохраняется в `.git/agent-memory-sync-status.json`, поэтому переживает
завершение MCP-процесса. Он не подтверждает, что синхронизация сейчас включена,
таймер работает или remote доступен. Статус `running`, оставшийся после сбоя,
сам по себе также не доказывает наличие живого процесса.

## Резервная копия и восстановление

Сохраните Markdown, `.agent-memory-history/` и экспортированную конфигурацию
владельца. Обычный Git sync исключает скрытую историю и не заменяет эту копию.
Проверьте `rebuild --config PATH` на новой тестовой SQLite, затем повторите
поиск, чтение структурированных знаний, связей и сохранённой истории.
Не используйте рабочую базу для проверки восстановления: `rebuild` заменяет
регистрации и индекс выбранной базы данными конфигурации.
